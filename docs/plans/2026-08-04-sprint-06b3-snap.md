# Sprint 06B.3 — Snap: implementation plan

**Spec:** `docs/specs/2026-08-04-sprint-06b3-snap-design.md` (frozen).

**No design decisions here.** If one appears — a change to the invariant so a factory can satisfy
it, a new assertion family, a tolerance — **stop and amend the spec**. 06B.1 needed that four
times, 06B.2 once, and both times the stop was worth more than the code that followed.

---

## What is different about this sprint

06B.1 extended solver evidence. 06B.2 opened integration evidence. **06B.3 does not know in
advance what it extends** — Task 1 exists to test whether a second integration invariant is needed
at all, and the answer decides the shape of everything after it.

So Task 1 is the sprint's real subject. Snap is the second subject, and only once the abstraction
has been shown to hold.

## Task 1: the refutation point

Write `SpringFactory` — and nothing else. No policy, no `SnapFactory`.

```kotlin
object SpringFactory {
    fun springTo(name: String, from: Float, to: Float, gestureVelocity: Float, spring: Spring): Animation
}
```

Its target is **supplied**, so it involves no new machinery and isolates the invariant from every
question about how `to` is obtained.

- [ ] It satisfies `IntegrationContract.assertTravelPreservesTheGestureVelocity` **unchanged**
- [ ] A witness that normalises by the wrong travel is shown red there, green on both other layers

**Stop condition, and it is the whole point of the sprint:** if the assertion must be edited for a
spring to pass it, Question 1 is refuted — integration does *not* begin once `to` exists, and the
spec is wrong. Stop, amend the spec, and decide whether a second invariant family is warranted
before writing another line.

Do not adjust the assertion to make this green. 06B.1 stopped to fix an oracle; 06B.2 stopped when
its named subject could not be built. Both stops were the sprint's most valuable output.

## Task 2: the policy layer

- [ ] `TargetSelectionPolicy` — a pure function of `(from, gestureVelocity, targets)`
- [ ] Its properties: `selectedTarget ∈ targets`, and it returns what the policy specifies
- [ ] Each has a witness (RULE-015)

These are **policy tests, not `IntegrationContract`**. They cross no unit boundary, need no
pipeline and no sampler. Adding them to the integration layer would dissolve the distinction that
layer was created to make.

## Task 3: `SnapFactory`

```
TargetSelectionPolicy  →  SpringFactory  →  SpringSampler
```

- [ ] It satisfies the same assertion, **still unchanged**
- [ ] `samplerFor` gains no branch — snap reuses `SpringSampler`, or the spec's prediction failed
      and that is recorded

**Stop condition:** any edit to the integration *invariant*. One law covering supplied, derived
and selected targets is the claim; changing the law to accommodate the third refutes it.
Generalising the *signature*, as Task 1 did, does not — but it must carry the argument that it is
the same law, and the burden is on the change.
